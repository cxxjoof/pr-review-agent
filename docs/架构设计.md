# AI PR Review 助手架构设计文档

## 一、文档说明

本文档用于说明 AI PR Review 助手的整体架构设计。项目目标是开发一个基于 Java Spring Boot 和大语言模型的 AI 代码评审工具。用户输入 GitHub 仓库地址和 PR 编号后，系统自动获取 Pull Request 的代码变更内容，并通过 AI 模型生成 PR 变更总结、风险代码识别、Review 建议和测试建议，最终在前端页面中展示完整的代码评审报告。

本文档主要包括系统总体架构、模块划分、核心流程、数据流设计、接口设计、数据库设计、AI 分析流程、安全设计和后续扩展方向。

## 二、系统总体架构

本项目采用前后端分离架构。

前端使用 React + Vite + Ant Design，负责用户输入、任务提交、加载状态展示和 Review 报告展示。

后端使用 Java 21 + Spring Boot 3.x，负责业务处理，包括 GitHub PR 数据获取、diff 解析、上下文构造、AI 模型调用、结果整理、数据存储和接口返回。

数据库使用 MySQL，负责保存 Review 任务、PR 信息、AI 分析结果和风险项。

外部服务主要包括 GitHub REST API 和大语言模型 API。GitHub REST API 用于获取 PR 基本信息和代码变更，大语言模型 API 用于完成代码理解和 Review 分析。

系统整体架构如下：

```text
用户浏览器
   ↓
React 前端页面
   ↓ HTTP 请求
Spring Boot 后端服务
   ↓
GitHub API 客户端  →  GitHub REST API
   ↓
PR 数据处理模块
   ↓
diff 解析模块
   ↓
上下文构造模块
   ↓
AI Review 分析模块  →  大语言模型 API
   ↓
结果整理模块
   ↓
MySQL 数据库
   ↓
返回 Review 报告
   ↓
React 前端展示
```

## 三、系统分层设计

后端采用典型的分层架构，主要分为 Controller 层、Service 层、Client 层、Repository 层和 Model 层。

### 1. Controller 层

Controller 层负责接收前端请求，并返回统一格式的响应结果。

主要职责包括：

1. 接收用户提交的仓库地址和 PR 编号；
2. 调用 Service 层创建 Review 任务；
3. 查询 Review 任务状态和分析结果；
4. 返回统一的 JSON 数据。

主要类设计：

```text
ReviewController
- createReviewTask()
- getReviewResult()
- listReviewTasks()

HealthController
- health()
```

Service 层负责核心业务逻辑，是系统最重要的一层。

主要职责包括：

1. 校验用户输入；
2. 创建 Review 任务；
3. 调用 GitHub API 获取 PR 数据；
4. 解析 PR diff；
5. 构造 AI 分析上下文；
6. 调用 AI 模型；
7. 整理 Review 报告；
8. 保存分析结果。

主要类设计：

```text

- getTaskById()
- listTasks()
```

### 3. Client 层

主要包括：

## 四、核心模块设计

### 1. PR 任务管理模块

该模块负责创建和管理 Review 分析任务。

当用户输入 GitHub 仓库地址和 PR 编号后，系统会生成一条 Review 任务记录。任务状态初始为 PENDING，分析开始后变为 RUNNING，分析成功后变为 SUCCESS，失败后变为 FAILED。

任务状态设计如下：

```text
PENDING：任务已创建，等待分析
RUNNING：任务正在分析中
SUCCESS：任务分析成功
FAILED：任务分析失败
```

第一版可以采用同步分析方式，也就是用户提交请求后，后端直接执行完整分析流程并返回结果。后续可以扩展为异步任务，前端通过任务 ID 轮询查询结果。

### 2. GitHub PR 数据获取模块

该模块负责根据用户输入的仓库地址和 PR 编号获取 PR 数据。

需要获取的数据包括：

1. PR 标题；
2. PR 描述；
3. PR 作者；
4. PR 分支信息；
5. 修改文件列表；
6. 每个文件的 patch/diff；
7. 新增行数和删除行数；
8. 提交记录。

第一版主要支持公开仓库。为了避免 GitHub API 频率限制，系统可以支持配置 GitHub Token。后续如果要支持私有仓库，则必须使用用户提供的 GitHub Token。

### 3. diff 解析模块

该模块负责解析 GitHub API 返回的 patch 内容。

主要处理内容包括：

1. 按文件拆分变更；
2. 提取新增代码行；
3. 提取删除代码行；
4. 保留上下文代码行；
5. 统计每个文件的修改行数；
6. 识别修改文件类型。

文件类型可以根据文件路径和后缀进行初步判断，例如：

```text
.java：Java 源代码
.yml / .yaml：配置文件
.sql：数据库脚本
.md：文档文件
.xml：Maven 配置或其他 XML 文件
.json：配置或数据文件
```

diff 解析的目标不是完整还原整个文件，而是为 AI 分析提供结构化的变更内容。

### 4. 上下文构造模块

AI 代码评审的准确性很大程度取决于上下文。因此系统需要对 PR 数据进行上下文构造，而不是直接把原始 diff 全部传给模型。

第一版上下文主要包括：

1. PR 标题；
2. PR 描述；
3. 修改文件列表；
4. 每个文件的 diff；
5. 文件新增行和删除行统计；
6. 文件类型；
7. 提交信息。

上下文构造时需要控制内容长度，避免超出模型上下文限制。对于大型 PR，可以按文件分批分析。

后续可以扩展为：

```text
PR diff + 文件完整内容 + 相关函数 + 测试文件 + 项目说明文档
```

更高级版本可以引入 RAG 代码检索，根据变更内容自动检索相关代码片段。

### 5. AI Review 分析模块

该模块是系统核心模块，负责调用大语言模型生成 Review 结果。

AI 分析主要分为四个部分：

第一，PR 变更总结。模型需要总结本次 PR 修改了什么、涉及哪些模块、可能影响哪些功能。

第二，风险代码识别。模型需要识别潜在 Bug、安全问题、异常处理缺失、边界条件不足、性能问题和配置风险。

第三，Review 建议生成。模型需要针对具体风险项给出可执行建议，而不是泛泛而谈。

第四，测试建议生成。模型需要根据变更内容提出应补充的测试点，例如单元测试、接口测试、边界测试和回归测试。

AI 输出建议采用结构化 JSON 格式，方便后端解析和前端展示。

建议 AI 输出结构如下：

```json
{
  "summary": "本次 PR 的整体变更总结",
  "changedModules": ["模块1", "模块2"],
  "riskItems": [
    {
      "filePath": "src/main/java/xxx/Service.java",
      "lineNumber": 42,
      "riskLevel": "HIGH",
      "riskType": "NULL_POINTER",
      "description": "风险描述",
      "suggestion": "修改建议"
    }
  ],
  "reviewSuggestions": [
    "建议一",
    "建议二"
  ],
  "testSuggestions": [
    "测试建议一",
    "测试建议二"
  ],
  "overallConclusion": "总体评价"
}
```

### 6. 结果整理模块

模型返回结果后，系统需要对结果进行整理和校验。

主要处理包括：

1. 校验 AI 返回 JSON 是否可解析；
2. 补充任务 ID、PR 信息和分析时间；
3. 将风险等级统一为 HIGH、MEDIUM、LOW；
4. 将风险项保存到数据库；
5. 生成前端需要的展示结构；
6. 对模型输出异常情况进行兜底处理。

如果 AI 返回格式不规范，后端可以进行简单修复，或者返回“模型输出解析失败”的错误状态。

前端主要分为三个页面：

1. GitHub 仓库地址输入框；

用户点击开始分析后，页面展示分析过程。

## 六、核心业务流程设计

### 1. 用户提交 PR 分析任务

流程如下：

```text
用户输入仓库地址和 PR 编号
↓
前端调用 POST /api/reviews
↓
后端校验参数
↓
创建 ReviewTask 任务
↓
调用 GitHub API 获取 PR 信息
↓
解析 diff 内容
↓
调用 AI 模型分析
↓
保存分析结果
↓
返回 Review 报告
```

### 2. 查询 Review 结果

流程如下：

```text
前端调用 GET /api/reviews/{id}
↓
后端查询 ReviewTask
↓
查询 PR 信息、Review 结果和风险项
↓
组装 ReviewResultResponse
↓
返回前端展示
```

### 3. AI 分析流程

AI 分析流程如下：

```text
PR 基本信息
↓
修改文件列表
↓
diff 解析结果
↓
构造 Prompt
↓
调用大语言模型
↓
获取结构化分析结果
↓
解析 JSON
↓
保存 Review 报告
```

如果 PR 文件较多，可以按文件分批分析：

```text
文件 1 diff → AI 分析 → 风险项 1
文件 2 diff → AI 分析 → 风险项 2
文件 3 diff → AI 分析 → 风险项 3
↓
汇总所有风险项
↓
生成最终 Review 报告
```

## 九、Prompt 构造设计

Prompt 是影响 AI Review 质量的关键部分。

Prompt 需要包含：

1. 角色设定：让模型扮演资深代码 Reviewer；
2. 任务目标：总结变更、识别风险、给出建议；
3. 输入内容：PR 标题、描述、文件列表和 diff；
4. 分析要求：避免泛泛而谈，不强行找问题；
5. 输出格式：要求返回结构化 JSON；
6. 风险等级定义：HIGH、MEDIUM、LOW；
7. 误报控制：证据不足时使用“建议确认”。

Prompt 的基本结构如下：

```text
你是一名资深代码评审专家，请根据以下 GitHub Pull Request 信息进行代码审查。

请完成以下任务：
1. 总结本次 PR 的主要变更；
2. 识别可能存在风险的代码；
3. 给出具体 Review 建议；
4. 给出建议补充的测试点；
5. 输出总体评价。

注意：
- 不要强行找问题；
- 只指出和本次 diff 直接相关的问题；
- 对证据不足的问题使用“建议确认”；
- 建议必须具体、可执行；
- 输出必须是 JSON 格式。

以下是 PR 信息：
……
```

## 十、误报与漏报控制设计

AI Review 工具需要控制误报和漏报。

### 1. 降低误报

降低误报的方式包括：

1. 只分析和本次 PR diff 相关的内容；
2. 要求模型说明风险依据；
3. 不对正常代码强行提出问题；
4. 对证据不足的问题使用“建议确认”；
5. 将代码风格类建议降低为 LOW 级别；
6. 优先关注 Bug、安全、稳定性和性能问题。

### 2. 降低漏报

降低漏报的方式包括：

1. 对认证、权限、数据库、配置文件等高风险文件提高关注；
2. 对删除逻辑、异常处理、输入校验等重点分析；
3. 对修改量较大的文件单独分析；
4. 后续引入完整文件上下文；
5. 后续引入 RAG 检索相关代码。

## 十一、安全设计

系统涉及 GitHub Token、模型 API Key 和代码内容，因此需要进行安全设计。

主要措施包括：

1. GitHub Token 和模型 API Key 使用环境变量配置；
2. 不将密钥写入代码仓库；
3. `.env`、`application-local.yml` 加入 `.gitignore`；
4. 日志中不打印 Token 和完整敏感代码；
5. 对仓库地址进行格式校验；
6. 对 PR 编号进行数字校验；
7. 私有仓库功能后续接入用户认证和权限控制；
8. 模型调用失败时不向前端暴露敏感错误信息。

## 十二、异常处理设计

系统需要统一处理异常。

常见异常包括：

1. 仓库地址格式错误；
2. PR 编号不存在；
3. GitHub API 调用失败；
4. GitHub API 访问频率限制；
5. 模型 API 调用失败；
6. AI 返回格式无法解析；
7. 数据库保存失败；
8. 任务分析超时。

后端可以使用：

```text
@RestControllerAdvice
```

实现全局异常处理，统一返回格式：

```json
{
  "code": 500,
  "message": "GitHub API 调用失败，请检查仓库地址或 PR 编号",
  "data": null
}
```

## 十三、部署架构设计

第一版项目可以采用本地部署。

## 十五、后续扩展设计

第一版重点完成核心链路：

```text
输入 GitHub PR → 获取 PR diff → AI 分析 → 展示 Review 报告
```

后续可以扩展以下能力：

1. GitHub Review Comment：将 AI 建议自动评论到 PR 页面；
2. 私有仓库支持：支持用户配置 GitHub Token；
3. 异步任务：使用 Redis 和线程池处理大型 PR；
4. RAG 代码检索：根据 diff 检索相关代码上下文；
5. 团队规则配置：支持自定义代码规范和 Review 规则；
6. 多模型支持：支持 DeepSeek、Qwen、GPT、Claude 等模型切换；
7. 历史问题学习：根据历史 Review 结果优化提示词；
8. 风险评分：根据风险项数量和严重程度生成 PR 风险分；
9. GitLab / Gitee 支持：扩展更多代码托管平台。

## 十六、架构设计总结

AI PR Review 助手采用前后端分离架构，前端使用 React + Vite + Ant Design，后端使用 Java 21 + Spring Boot 3.x，数据库使用 MySQL，外部接入 GitHub REST API 和大语言模型 API。

系统核心架构围绕“PR 数据获取、diff 解析、上下文构造、AI 分析、结果展示”展开。通过分层架构设计，系统可以保持较好的可维护性和扩展性。第一版重点保证核心流程完整可运行，后续再逐步扩展异步任务、自动 PR 评论、RAG 代码检索、私有仓库支持和团队规则配置等能力。

本项目的定位不是完全替代人工代码审查，而是作为辅助工具，帮助开发者快速理解 PR 内容，提前发现明显风险，提高 Pull Request Review 的效率和质量。
