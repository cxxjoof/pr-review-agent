# AI PR Review 助手模块拆分与开发计划文档

## 一、文档说明

本文档用于指导 AI PR Review 助手项目的模块拆分、开发顺序、Commit 提交和 PR 提交。项目采用 Java + Spring Boot 作为后端主技术栈，React + Vite + Ant Design 作为前端技术栈，MySQL 作为数据库，外部接入 GitHub REST API 和大语言模型 API。

本项目功能较多，如果一次性完成所有代码，容易导致 PR 过大、代码难以 Review、问题难以定位。因此项目开发应按照模块逐步推进，每个 PR 只完成一个明确功能，保证主分支在每次合并后都能正常运行。

## 二、整体模块划分

本项目可以拆分为以下 10 个核心模块：

```text
1. 项目基础结构模块
2. 后端基础服务模块
3. 前端基础页面模块
4. 数据库与实体模块
5. GitHub PR 数据获取模块
6. Diff 解析与上下文构造模块
7. AI 模型调用模块
8. AI Review 分析模块
9. 前端 Review 交互展示模块
10. 异常处理、文档与演示模块
```

整体开发顺序建议如下：

```text
项目初始化
↓
后端基础服务
↓
前端基础页面
↓
数据库表结构
↓
GitHub PR 数据获取
↓
Diff 解析
↓
AI 模型调用
↓
AI Review 分析
↓
前端结果展示
↓
异常处理与文档完善
```

## 十六、AI Coding 使用建议

使用 AI Coding 时，不建议一次性让 AI 完成整个项目。应该按模块给 AI 下任务，每次只让它完成一个 PR 的内容。

### 1. 推荐提示词模板

```text
你现在是我的 Java Spring Boot 项目开发助手。

项目名称：AI PR Review 助手。
当前只开发一个模块，不要实现其他模块。
本次任务对应一个独立 PR，要求每个 PR 只做一件事。

本次开发模块：
【填写模块名称】

本次要实现的内容：
【填写本模块的具体功能】

技术栈：
后端：Java 21 + Spring Boot 3.x + MySQL + Spring Data JPA
前端：React + Vite + Ant Design
外部接口：GitHub REST API、OpenAI 兼容模型 API

开发要求：
1. 只修改和本模块相关的文件；
2. 不要提前实现后续模块；
3. 代码结构要符合 controller、service、client、repository、entity、dto 分层；
4. 不要把 API Key、Token 写死在代码中；
5. 给出本次修改的文件列表；
6. 给出本次功能的测试方式；
7. 给出建议 commit message；
8. 保证本次修改后项目仍然可以启动运行。
```

### 2. 示例：让 AI 开发 GitHub PR 数据获取模块

```text
你现在是我的 Java Spring Boot 项目开发助手。
```

## 十七、Commit 提交规范

每个 PR 内可以包含多个 commit，但每个 commit 也应该尽量小而清晰。

推荐格式：

```text
<type>: <description>
```

常见 type：

```text
feat：新增功能
fix：修复问题
docs：文档修改
chore：工程配置
test：测试相关
refactor：重构
style：格式调整
```

示例：

```text
feat: add github api client
feat: add pull request dto
fix: handle github api error response
docs: update github integration usage
```

不推荐：

```text
update code
fix bug
修改一下
最终版
```

## 十八、每个 PR 合并前检查清单

每个 PR 合并前，都要检查：

```text
1. 本 PR 是否只做了一件事？
2. PR 标题是否清晰？
3. PR 描述是否包含功能描述、实现思路、测试方式？
4. 是否提交了不相关文件？
5. 是否提交了 API Key、Token、.env 等敏感文件？
6. 后端是否能启动？
7. 前端是否能启动？
8. 本 PR 的功能是否能被验证？
9. README 或 docs 是否需要同步更新？
10. 主分支合并后是否仍能运行？
```

## 十九、主分支可运行要求

每次 PR 合并后，主分支都必须保持可运行状态。

最低要求：

```text
- backend 可以 mvn spring-boot:run 正常启动
- frontend 可以 npm run dev 正常启动
- README 中运行命令仍然有效
- 没有明显编译错误
- 没有提交本地临时文件
- 没有提交密钥
```

如果某个模块尚未接入完整流程，也要保证已有功能不被破坏。

## 二十、总结

本项目应按照模块化方式逐步开发，避免一次性提交大而混乱的 PR。推荐从项目结构、后端基础、前端基础、数据库模型、GitHub 数据获取、diff 解析、AI 模型调用、AI Review 分析、前端展示、异常处理和文档演示等模块依次推进。

这种拆分方式可以保证：

```text
1. 每个 PR 都清晰、独立、可 Review；
2. 每个阶段都有可运行成果；
3. AI Coding 不容易跑偏；
4. Commit 和 PR 记录方便后续回顾；
5. 评委可以清楚看到项目从 0 到 1 的开发过程。
```
