# AI PR Review 助手技术选型文档

> Source PDF: `AI PR Review 助手技术选型文档.pdf`

## 一、项目技术目标

AI PR Review 助手的目标是开发一个基于 AI 的代码评审工具。用户输入 GitHub 仓库地址和 PR 编号后，系统 自动获取该 Pull Request 的代码变更内容，并调用大语言模型进行分析，最终生成 PR 变更总结、风险代码识 别、Review 建议和测试补充建议。 本项目选择 Java 作为主编程语言，主要是因为项目不仅仅是一个简单的 AI 调用 Demo，而是一个具有完整后 端服务能力的工程化系统。Java 在 Web 后端开发、接口设计、分层架构、数据库集成、异步任务、配置管理 和系统扩展方面更加成熟，适合作为本项目的主体开发语言。

## 二、整体技术架构

本项目采用前后端分离架构。 前端负责用户输入和结果展示，后端负责 GitHub PR 数据获取、代码 diff 解析、上下文构造、AI 模型调用、 Review 报告生成和结果存储。 整体流程如下： 用户浏览器 → 前端页面 → Java 后端服务 → GitHub API 获取 PR 信息 → 解析 PR diff → 构造 AI 分析上下文 → 调用大语言模型 → 生成结构化 Review 报告 → 返回前端展示

## 三、主编程语言选型：Java

### 1. 选择 Java 的原因

本项目选择 Java 作为主编程语言，主要有以下原因： 第一，Java 适合开发稳定的后端服务。本项目需要提供 API 接口、处理请求、调用第三方服务、管理任务状态 和存储分析结果，这些都属于典型的后端开发场景，Java 具备成熟的工程化能力。 第二，Java 生态成熟。Spring Boot、Spring Web、Spring Data JPA、MyBatis、Redis、Security 等生态可 以很好地支持本项目后续扩展，例如用户登录、任务队列、数据库管理、权限控制和接口文档生成。 第三，Java 更适合作为简历项目或工程项目展示。相比只使用 Python 快速调用模型，Java 后端可以体现更完 整的软件工程能力，包括分层架构、接口设计、异常处理、数据库设计、配置管理和部署能力。 第四，AI 模型调用本质上是 HTTP API 调用。虽然 Python 在 AI 生态中更常见，但本项目主要是调用大模型接 口，而不是训练模型。因此 Java 通过 WebClient、OkHttp 或 OpenFeign 也可以很好地完成模型接入。 第五，Java 适合长期维护。项目后续如果要扩展为 GitHub Bot、团队代码审查平台或企业级工具，Java 的稳 定性和可维护性更有优势。

### 2. Java 版本选择

推荐使用： Java 21 选择 Java 21 的原因是它是长期支持版本，性能、语法和生态支持都比较成熟。对于课程项目或个人项目，也 可以使用 Java 17，因为 Java 17 同样是长期支持版本，兼容性较好。 本项目推荐： Java 21 + Spring Boot 3.x

## 四、后端技术选型

### 1. 后端框架：Spring Boot

后端框架选择 Spring Boot。Spring Boot 是 Java 后端开发中最常用的框架之一，适合快速搭建 RESTful API 服务。 本项目中，Spring Boot 主要负责： 提供前端调用的 API 接口； 接收用户输入的 GitHub 仓库地址和 PR 编号； 调用 GitHub API 获取 PR 数据； 调用 AI 模型 API 生成分析结果； 管理 Review 任务状态； 将分析结果返回给前端； 后续扩展数据库、Redis、权限认证和异步任务。 选择 Spring Boot 的原因： 开发效率高； 工程结构清晰； 生态成熟； 适合 REST API 开发； 后续扩展方便。

### 2. 接口开发：Spring Web

系统后端对外提供 REST API，因此选择 Spring Web 作为接口开发模块。 建议设计以下接口： POST /api/reviews 提交 PR Review 分析任务 GET /api/reviews/{id} 查询某次 Review 分析结果 GET /api/reviews 查询历史 Review 记录 GET /api/health 健康检查接口 后续如果接入 GitHub 自动评论，可以增加： POST /api/reviews/{id}/comments 将 AI Review 结果评论到 GitHub PR

### 3. HTTP 客户端：Spring WebClient

系统需要调用两个外部服务： GitHub REST API； 大语言模型 API。 推荐使用 Spring WebClient 作为 HTTP 客户端。WebClient 支持同步和异步调用，适合后续扩展并发请求和异 步分析任务。 如果第一版想简单实现，也可以使用 OkHttp。两者都可以，但从 Spring Boot 项目整体一致性来看， WebClient 更适合。 推荐选择： Spring WebClient

### 4. 数据访问层：Spring Data JPA 或 MyBatis-Plus

本项目需要保存 Review 任务、PR 信息、分析结果和风险项。数据访问层可以选择 Spring Data JPA 或 MyBatis-Plus。 如果项目表结构简单，推荐使用 Spring Data JPA，开发速度更快。 如果希望 SQL 更直观、方便自己控制查询语句，也可以使用 MyBatis-Plus。 本项目推荐： Spring Data JPA 原因是第一版功能主要是保存和查询 Review 结果，业务查询不复杂，JPA 可以减少重复代码。

## 五、前端技术选型

### 1. 前端框架：React

前端推荐使用 React。React 适合组件化开发，可以把页面拆成 PR 输入组件、任务状态组件、变更总结组件、 风险列表组件和 Review 建议组件。 主要页面包括： 首页输入 GitHub 仓库地址和 PR 编号； Review 结果页展示分析报告； 历史记录页展示过去的分析任务； 风险详情区域展示具体文件、代码位置和建议。 选择 React 的原因： 生态成熟； 组件化开发方便； 适合构建工具类页面； 后续扩展性强。

### 2. 构建工具：Vite

前端构建工具选择 Vite。Vite 启动快、配置简单，适合本项目快速开发。 推荐技术组合： React + Vite

### 3. UI 组件库：Ant Design

UI 组件库推荐使用 Ant Design。它适合开发后台管理系统和工具平台，能够快速完成表单、卡片、表格、标 签、提示信息等页面元素。 本项目可以使用： Input 输入仓库地址和 PR 编号； Button 触发分析； Card 展示 PR 总结； Table 展示风险代码； Tag 标记风险等级； Collapse 展示详细建议； Spin 展示加载状态。 推荐选择： Ant Design

## 六、数据库技术选型

### 1. 第一阶段：MySQL

由于本项目选择 Java + Spring Boot 作为主技术栈，数据库推荐使用 MySQL。MySQL 生态成熟，和 Spring Boot 集成简单，适合存储 Review 任务和分析结果。 主要数据表可以包括： review_task：Review 任务表； pull_request_info：PR 基本信息表； review_result：AI 分析结果表； risk_item：风险项表； model_call_log：模型调用记录表。 选择 MySQL 的原因： 使用广泛； 和 Java 后端适配成熟； 适合项目展示； 方便后续扩展用户系统和历史记录。

### 2. 开发阶段可选：H2 或 SQLite

如果只是本地快速开发，也可以先使用 H2 内存数据库或 SQLite。这样不需要额外安装数据库，方便快速调 试。 但最终项目展示建议使用： MySQL 这样更像完整工程项目。

## 七、GitHub 接入技术选型

### 1. GitHub REST API

系统需要通过 GitHub REST API 获取 PR 数据，包括 PR 标题、描述、作者、变更文件、diff 内容和提交信息。 主要调用内容包括： 获取 PR 基本信息； 获取 PR 修改文件列表； 获取每个文件的 patch 内容； 获取 PR commits； 后续获取文件完整内容； 后续提交 Review Comment。 第一版主要支持公开仓库，可以不强制配置 GitHub Token。但为了避免 GitHub API 频率限制，建议支持用户 配置 Token。

### 2. GitHub Token 管理

如果用户需要分析私有仓库，就必须提供 GitHub Token。Token 不应该写死在代码中，应通过环境变量或配置 文件读取。 推荐配置方式： GITHUB_TOKEN=xxxx 并且 .env、application-local.yml 等敏感配置文件不能提交到 GitHub。

## 八、AI 模型接入技术选型

### 1. 模型接入方式：OpenAI 兼容接口

本项目推荐采用 OpenAI 兼容接口接入大语言模型。这样后续可以比较方便地切换不同模型，例如 DeepSeek、 Qwen、OpenAI、Claude 或其他兼容接口模型。 模型调用可以统一封装成一个服务类： AiReviewService

- generatePrSummary()
- detectRiskCode()
- generateReviewSuggestions()
再单独封装模型客户端： ModelClient

- chatCompletion()
这样做的好处是业务逻辑和模型厂商解耦。后续换模型时，不需要大改业务代码。

### 2. 推荐模型

第一版可以选择代码理解能力较强、成本可控的模型，例如： DeepSeek 系列； Qwen 系列； GPT 系列； Claude 系列。 如果是课程项目，推荐优先选择 OpenAI 兼容接口的模型，接入简单，切换方便。

### 3. 模型调用策略

为了避免一次性输入内容过长，系统不建议把整个 PR 的所有 diff 一次性丢给模型。推荐采用分层分析方式： 第一步，分析 PR 的整体信息，生成变更总结； 第二步，按文件或代码块分析 diff，识别风险项； 第三步，汇总所有风险项，生成最终 Review 报告； 第四步，根据代码变更生成测试建议。 这种方式可以提高分析准确性，也可以减少模型上下文过长导致的遗漏问题。

## 九、diff 解析与上下文处理技术选型

### 1. diff 解析方式

GitHub API 返回的 PR 文件信息中通常包含 patch 字段，可以从中提取新增行、删除行和上下文行。 Java 中可以先使用字符串解析完成第一版功能，例如按文件、按行解析 diff 内容，识别 + 新增行和 - 删除 行。 后续可以引入 Java diff 解析库，例如： java-diff-utils 它可以辅助处理文本差异、构造 diff 结果和生成变更片段。

### 2. 上下文获取方式

第一版系统可以采用： PR diff 优先分析 即主要分析本次 PR 修改的代码内容，保证实现简单、响应速度快。 后续可以升级为： diff + 文件完整内容 + 相关上下文 系统根据修改文件路径，通过 GitHub API 获取完整文件内容，让 AI 不只看变更行，还能结合函数、类和模块 上下文进行判断。 更高级的版本可以引入代码索引和 RAG 检索，根据变更内容自动召回相关代码片段，例如被调用函数、接口定 义、测试文件和配置文件。

## 十、异步任务技术选型

### 1. 第一阶段：同步处理

第一版可以先使用同步接口。用户提交 PR 信息后，后端立即获取 GitHub 数据、调用模型并返回结果。 这种方式实现简单，适合小型 PR 和项目原型。

### 2. 后续扩展：Spring Task + Redis

如果 PR 较大或模型调用时间较长，可以改为异步任务。 推荐方案： Spring Task / ThreadPoolTaskExecutor + Redis 用户提交 Review 后，后端先创建任务并返回任务 ID，前端通过任务 ID 查询分析状态。 任务状态可以包括： PENDING RUNNING SUCCESS FAILED 后续如果任务量更大，也可以使用 RabbitMQ、Kafka 或 Redis Stream 做消息队列。

## 十一、安全技术选型

本项目涉及 GitHub Token、模型 API Key 和代码内容，因此需要注意安全设计。 主要措施包括： GitHub Token 和模型 API Key 使用环境变量管理； 不把密钥写死在代码中； .env、application-local.yml 等文件加入 .gitignore； 日志中不打印 Token 和完整敏感代码； 对用户输入的仓库地址和 PR 编号进行校验； 对私有仓库代码分析结果进行权限控制； 后续可以接入 Spring Security 做登录认证。 第一版如果只支持公开仓库，可以先不做复杂权限系统，但密钥保护必须保留。

## 十二、接口文档技术选型

为了方便前后端联调，推荐使用 Swagger / OpenAPI 生成接口文档。 在 Spring Boot 项目中可以使用： springdoc-openapi 它可以自动生成接口文档，前端可以直接查看接口参数和返回格式。 推荐接口文档地址： /swagger-ui.html

## 十三、日志与异常处理技术选型

后端使用 Spring Boot 默认日志体系即可，底层通常基于 Logback。 需要记录的日志包括： 用户提交的仓库地址和 PR 编号； GitHub API 调用是否成功； 模型调用是否成功； Review 任务状态变化； 异常错误信息。 需要注意的是，日志中不能输出 GitHub Token、模型 API Key 或其他敏感信息。 异常处理可以使用 Spring Boot 的全局异常处理机制： @RestControllerAdvice 统一返回错误信息，例如： 仓库地址格式错误 PR 不存在 GitHub API 调用失败 模型调用失败 分析任务超时

## 十四、部署技术选型

### 1. 本地开发部署

开发阶段推荐本地运行： 前端：React + Vite 后端：Spring Boot 数据库：MySQL 模型 Key：环境变量

### 2. 容器化部署：Docker

后续可以使用 Docker 部署项目，保证环境一致。 推荐使用 Docker Compose 管理服务： frontend backend mysql redis 第一版可以只部署： backend + mysql 如果前端单独部署，也可以使用 Vercel、Nginx 或静态服务器部署前端页面。

## 十五、推荐技术栈总结

本项目最终推荐技术栈如下： 前端： React + Vite + Ant Design + Axios 后端： Java 21 + Spring Boot 3.x Spring Web Spring WebClient Spring Data JPA springdoc-openapi 数据库： MySQL AI 模型： OpenAI 兼容接口 DeepSeek / Qwen / GPT / Claude 等代码能力较强的模型 GitHub 接入： GitHub REST API GitHub Token 异步扩展： Spring Task / ThreadPoolTaskExecutor Redis 部署： Docker Docker Compose 后续扩展： GitHub Review Comment Spring Security RAG 代码检索 向量数据库 GitLab / Gitee 支持 团队自定义 Review 规则

## 十六、技术选型结论

综合项目目标和后续扩展需求，本项目选择 Java 作为主编程语言，后端采用 Spring Boot 构建 REST API 服 务，前端采用 React + Vite + Ant Design 构建用户界面，数据库使用 MySQL 存储 Review 任务和分析结果，AI 模型通过 OpenAI 兼容接口接入，GitHub 数据通过 GitHub REST API 获取。 相比 Python 快速原型方案，Java + Spring Boot 更适合本项目作为一个完整工程项目进行开发。它不仅能够完 成 AI 代码评审的核心功能，还能体现良好的后端架构设计、接口设计、数据存储、异常处理、安全配置和部署 能力。 第一版开发重点应放在核心链路上： 输入 GitHub PR → 获取 PR diff → 调用 AI 模型分析 → 生成 Review 报告 → 前端展示结果 后续再逐步扩展异步任务、GitHub 自动评论、私有仓库支持、RAG 代码检索和团队规则配置等能力。
