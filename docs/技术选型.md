# AI PR Review 助手技术选型文档

## 一、项目技术目标

AI PR Review 助手的核心目标是：用户输入 GitHub 仓库地址和 PR 编号后，系统能够自动获取该 PR 的代码变更内容，并调用 AI 模型进行智能分析，最终生成 PR 变更总结、风险代码识别、Review 建议和测试补充建议。

因此，技术选型需要重点满足以下要求：

1. 能够方便调用 GitHub API 获取 PR 数据；
2. 后端能够稳定处理代码 diff、上下文拼接和 AI 调用；
3. 前端界面要简洁清晰，方便展示 Review 结果；
4. AI 模型需要具备较好的代码理解能力；
5. 系统结构要方便后续扩展，例如支持私有仓库、GitLab、RAG 检索和自动评论 PR。

## 二、整体技术架构

本项目采用前后端分离架构。

前端负责用户输入、任务提交和结果展示；后端负责调用 GitHub API、解析 PR diff、构造提示词、调用 AI 模型并整理分析结果；AI 模型负责代码理解、风险识别和 Review 建议生成。

整体架构如下：

用户浏览器
→ 前端页面
→ 后端服务
→ GitHub API 获取 PR 数据
→ diff 解析与上下文处理
→ AI 模型分析
→ 返回结构化 Review 报告
→ 前端展示结果

## 三、前端技术选型

### 1. 前端框架：React

前端推荐使用 React。React 生态成熟，组件化能力强，适合开发交互型 Web 工具。本项目中，前端页面主要包括 PR 输入区、分析按钮、加载状态、Review 结果展示区和风险项列表，使用 React 可以较方便地拆分组件。

选择 React 的原因：

1. 组件化开发方便；
2. 生态成熟，资料多；
3. 适合快速开发 Web 工具；
4. 后续可以方便扩展成管理后台或插件页面。

### 2. 构建工具：Vite

Vite 启动速度快，配置简单，适合中小型前端项目。本项目开发初期页面数量不多，使用 Vite 可以减少复杂配置，提高开发效率。

选择 Vite 的原因：

1. 项目启动快；
2. 热更新速度快；
3. 配置比传统 Webpack 简单；
4. 适合快速原型开发。

### 3. UI 组件库：Ant Design

前端页面可以使用 Ant Design。它提供了输入框、按钮、卡片、表格、标签、提示框、加载动画等常用组件，适合快速搭建后台工具类页面。

在本项目中可以使用：

1. Input 输入 GitHub 仓库地址和 PR 编号；
2. Button 触发分析；
3. Card 展示 PR 总结；
4. Table 展示风险代码列表；
5. Tag 区分高、中、低风险；
6. Collapse 展示详细建议。

选择 Ant Design 的原因：

1. 组件完整；
2. 风格适合工具类系统；
3. 开发效率高；
4. 易于维护。

## 四、后端技术选型

### 1. 后端语言：Java 21

后端使用 Java 21。根据 `AGENTS.md` 和模块拆分计划，本项目后端主技术栈明确为 Java 21 + Spring Boot 3.x，需要围绕后续的分层架构、数据库持久化、GitHub API 调用和 AI 模型集成进行工程化实现。

选择 Java 21 的原因：

1. 与项目既定技术栈保持一致，避免文档与实现方向冲突；
2. 适合构建结构清晰、可维护的企业级后端服务；
3. 与 Spring Boot 3.x、Spring Data JPA、Spring WebClient 配合成熟；
4. 方便按 `controller / service / client / repository / dto` 分层推进后续模块；
5. 有利于项目在每个模块阶段都保持可运行、可测试状态。

### 2. 后端框架：Spring Boot 3.x

后端框架使用 Spring Boot 3.x，并配合 Maven 进行项目构建与依赖管理。按照模块拆分计划，后端会先完成基础启动与健康检查，再逐步接入数据库、GitHub PR 获取、diff 解析、模型调用和 Review 任务接口。

后端主要使用的 Spring 技术包括：

1. Spring Web：提供 REST API；
2. Spring Data JPA：处理数据库访问；
3. Spring WebClient：调用 GitHub REST API 和 OpenAI 兼容模型接口；
4. Spring Boot Test：完成基础接口与上下文测试。

本项目可以设计以下接口：

1. `POST /api/reviews`：提交仓库地址和 PR 编号，创建 Review 任务；
2. `GET /api/reviews/{id}`：查询分析结果；
3. `GET /api/reviews`：查询任务列表；
4. `GET /api/health`：系统健康检查。

选择 Spring Boot 的原因：

1. 与 `AGENTS.md` 规定的后端技术栈完全一致；
2. 能快速搭建可运行的后端基础服务；
3. 分层结构清晰，适合逐模块扩展；
4. 与 MySQL、JPA、WebClient 等后续模块衔接自然；
5. 方便后续补充统一异常处理、配置管理和接口测试。

### 3. GitHub 数据获取：GitHub REST API

系统需要通过 GitHub REST API 获取 PR 信息、文件变更和 diff 内容。第一阶段主要支持公开仓库，因此可以先不强制要求 GitHub Token；如果遇到访问频率限制或私有仓库，再加入 Token 配置。

主要获取内容包括：

1. PR 基本信息；
2. PR 修改文件列表；
3. 每个文件的 patch/diff；
4. PR 标题和描述；
5. 提交记录；
6. 后续可扩展获取完整文件内容。

选择 GitHub REST API 的原因：

1. 官方接口稳定；
2. 文档完善；
3. 能直接获取 PR 文件变更；
4. 适合第一版快速实现。

## 五、AI 模型技术选型

### 1. 模型方案：OpenAI 兼容接口

第一版建议使用 OpenAI 兼容接口形式接入模型。这样后续可以比较方便地切换不同模型，例如 DeepSeek、Qwen、OpenAI、Claude 或其他兼容平台。

推荐采用统一的模型调用封装层，例如：

```text
ModelClient
- analyze_pr_summary()
- analyze_risk_code()
- generate_review_suggestions()
```

这样业务代码不直接绑定某一个模型厂商，后续换模型时只需要修改模型配置。

选择 OpenAI 兼容接口的原因：

1. 接入方式通用；
2. 方便切换模型；
3. 降低厂商绑定；
4. 方便做多模型对比。

### 2. 推荐模型类型

第一阶段可以选择代码理解能力较强、调用成本可控的模型，例如：

1. DeepSeek 系列模型；
2. Qwen 系列模型；
3. GPT 系列模型；
4. Claude 系列模型。

如果是课程项目或原型系统，可以优先选择成本较低、响应速度较快的模型；如果要提高 Review 准确率，可以使用更强的模型处理重点文件。

### 3. 模型调用策略

为了平衡准确性和速度，可以采用分层调用策略：

第一步，使用模型生成 PR 总体变更总结；

第二步，按文件分析代码 diff，识别潜在风险；

第三步，将所有风险项汇总，让模型生成最终 Review 报告。

对于大型 PR，不建议一次性把所有 diff 都发送给模型，否则容易超出上下文限制，也会降低分析质量。可以按文件或按代码块拆分，再汇总结果。

## 六、数据存储技术选型

### 1. 第一阶段：MySQL

第一阶段数据库使用 MySQL。根据 `AGENTS.md` 和模块拆分计划，项目需要围绕 MySQL 与 Spring Data JPA 建立 `review_task`、`pull_request_info`、`review_result`、`risk_item`、`model_call_log` 等核心表，为后续 Review 任务和分析结果持久化提供支撑。

可存储内容包括：

1. 用户提交的仓库地址和 PR 编号；
2. PR 基本信息；
3. Review 任务状态；
4. AI 分析结果；
5. 风险项列表；
6. 模型调用日志；
7. 创建时间和更新时间。

选择 MySQL 的原因：

1. 与项目既定数据库技术栈一致；
2. 便于配合 Spring Data JPA 建立实体与仓库层；
3. 适合保存结构化任务数据和分析结果；
4. 方便后续扩展任务查询、结果展示和统计分析能力。

### 2. 持久化实现：Spring Data JPA

数据库访问层使用 Spring Data JPA，减少重复 SQL 编写，便于快速建立 Entity 和 Repository，并保持后端分层结构清晰。

## 七、代码解析与上下文处理技术选型

### 1. diff 解析：Java 服务内解析

系统需要解析 GitHub 返回的 patch 内容，提取新增行、删除行、文件路径和代码位置。第一版建议直接在 Java 后端的 `DiffParseService` 中完成解析，优先使用可控的字符串处理和结构化封装方式，满足模块拆分计划中对 diff 解析与上下文构造的要求。

这样做的原因是：

1. 与既定 Java 后端技术栈保持一致；
2. 避免为了单一能力引入与主栈不一致的 Python 方案；
3. 便于后续直接与 DTO、Service 和 AI 上下文构造模块衔接。

### 2. 上下文获取：GitHub Contents API

第一版主要分析 PR diff。后续为了提高准确性，可以通过 GitHub Contents API 获取被修改文件的完整内容，让 AI 不只看变更行，还能理解函数、类和模块上下文。

上下文获取策略可以分为三层：

1. 基础层：只获取 PR diff；
2. 增强层：获取被修改文件完整内容；
3. 高级层：检索相关函数、调用链、测试文件和项目说明文档。

### 3. 后续扩展：RAG + 向量数据库

如果项目规模较大，可以引入 RAG 检索。系统把代码文件切片后转为向量，存入向量数据库。分析 PR 时，根据变更内容检索相关代码片段，再提供给模型。

可选向量数据库包括：

1. Chroma；
2. Milvus；
3. Qdrant；
4. FAISS。

第一版不建议直接做 RAG，因为实现复杂度较高。可以先完成 diff 分析和文件上下文获取，后续再扩展。

## 八、任务处理技术选型

### 1. 第一阶段：同步接口

如果 PR 较小，可以直接使用同步接口处理。用户提交 PR 信息后，后端立即获取数据、调用模型并返回分析结果。

优点是实现简单，适合第一版。

缺点是大型 PR 分析时间较长，用户可能等待较久。

### 2. 后续扩展：异步任务处理

如果后续要支持大型 PR 或多人同时使用，可以在 Java / Spring 体系内扩展异步任务处理能力。用户提交任务后，系统先返回任务 ID，后端异步执行分析，前端轮询任务状态。

推荐扩展方案：

1. 使用 Spring 的异步能力或线程池处理长耗时任务；
2. 结合 Redis 作为缓存或任务状态辅助组件；
3. 前端轮询查询任务状态和分析结果。

## 九、部署技术选型

### 1. 本地开发部署

开发阶段可以使用本地运行方式：

1. 前端：Vite 本地启动；
2. 后端：Spring Boot 本地启动；
3. 数据库：MySQL 本地服务；
4. 模型 Key：使用环境变量或本地忽略配置文件管理。

适合个人开发和课程演示。

### 2. 容器化部署：Docker

后续可以使用 Docker 部署前后端服务。Docker 可以保证环境一致，方便在不同机器上运行。

推荐服务拆分：

1. frontend：前端服务；
2. backend：Spring Boot 后端 API；
3. mysql：数据库服务；
4. redis：后续异步任务扩展使用。

### 3. 部署平台

如果是演示项目，可以部署在：

1. 本地电脑；
2. 云服务器；
3. Render；
4. Vercel + 后端云服务；
5. Docker Compose 环境。

第一版建议先本地运行，等功能稳定后再使用 Docker Compose 部署。

## 十、安全技术选型

系统需要注意 GitHub Token、模型 API Key 和代码内容安全。

安全设计包括：

1. API Key 不写死在代码里；
2. 使用 `.env` 文件或环境变量管理密钥；
3. `.env` 必须加入 `.gitignore`；
4. 后端不在日志中打印 Token；
5. 私有仓库代码不随意保存；
6. 对用户输入的仓库地址和 PR 编号做基本校验；
7. 后续支持用户级权限控制。

如果只是公开仓库演示项目，可以先简化认证，但仍然要避免把模型 Key 提交到 GitHub。

## 十二、技术选型结论

综合项目需求、开发难度和后续扩展性，并结合 `AGENTS.md` 与模块拆分计划，本项目建议采用 React + Vite + Ant Design 构建前端页面，使用 Java 21 + Spring Boot 3.x 构建后端服务，通过 GitHub REST API 获取 PR 数据，并使用 OpenAI 兼容接口接入大语言模型完成代码评审分析。

第一版系统应优先保证核心流程跑通，即“输入 PR → 获取 diff → AI 分析 → 返回 Review 报告”。在此基础上，再逐步扩展上下文检索、异步任务、私有仓库支持、GitHub 自动评论和 RAG 代码检索能力。

这种技术选型整体较轻量，开发成本低，适合从 0 到 1 快速实现 AI PR Review 助手，同时也保留了后续升级为完整工程化系统的空间。
