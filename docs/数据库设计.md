# AI PR Review 助手数据库设计文档

> Source PDF: `AI PR Review 助手数据库设计文档.pdf`

## 一、文档说明

本文档用于说明 AI PR Review 助手项目的数据库设计。系统主要功能是用户输入 GitHub 仓库地址和 PR 编号 后，后端自动获取 PR 信息、解析代码变更、调用 AI 模型分析，并生成 PR 变更总结、风险代码识别、Review 建议和测试建议。 本项目后端采用 Java + Spring Boot，数据库采用 MySQL。数据库主要用于保存 Review 分析任务、Pull Request 基本信息、AI 分析结果、风险代码项和模型调用记录。

## 二、数据库设计目标

数据库设计需要满足以下目标： 能够保存用户提交的 PR Review 分析任务； 能够记录每个任务的执行状态； 能够保存 GitHub PR 的基本信息； 能够保存 AI 生成的 Review 报告； 能够保存风险代码识别结果； 能够记录模型调用日志，方便后续排查问题； 能够支持历史 Review 记录查询； 方便后续扩展用户系统、私有仓库、GitHub 自动评论和团队规则配置。

## 三、数据库选型

本项目选择 MySQL 作为主要数据库。 选择 MySQL 的原因： 使用广泛，生态成熟； 与 Java Spring Boot 集成方便； 适合存储结构化业务数据； 支持事务、索引和复杂查询； 适合项目后续扩展为多人使用的 Web 系统。 开发阶段也可以使用 H2 或 SQLite 进行快速测试，但正式项目建议使用 MySQL。

## 四、数据库整体表结构

本项目第一版主要设计 5 张核心表： review_task Review 分析任务表 pull_request_info Pull Request 基本信息表 review_result AI Review 结果表 risk_item 风险代码项表 model_call_log 模型调用日志表 表之间的关系如下： review_task 1 —— 1 pull_request_info review_task 1 —— 1 review_result review_task 1 —— N risk_item review_task 1 —— N model_call_log 也就是说，一个 Review 任务对应一个 PR 基本信息，一个最终 Review 报告，多个风险项，以及多条模型调用 记录。

## 五、核心实体关系说明

### 1. review_task 与 pull_request_info

review_task 表保存任务本身的信息，例如仓库地址、PR 编号、任务状态等。 pull_request_info 表保存从 GitHub API 获取到的 PR 详细信息，例如 PR 标题、作者、分支、修改文件数 量、新增行数和删除行数等。

## 二者是一对一关系。

### 2. review_task 与 review_result

review_result 表保存 AI 最终生成的分析报告，包括变更总结、Review 建议、测试建议和总体评价。

## 一个任务最终生成一份 Review 报告，所以二者是一对一关系。

### 3. review_task 与 risk_item

risk_item 表保存 AI 识别出的风险代码项。一个 PR 中可能存在多个风险项，所以一个任务对应多个风险项。

## 二者是一对多关系。

### 4. review_task 与 model_call_log

AI 分析过程中可能多次调用模型，例如先生成变更总结，再分析风险代码，最后生成整体报告。因此一个任务 可能对应多条模型调用日志。

## 二者是一对多关系。

## 七、表关系设计

### 1. 关系说明

review_task 是主表，其他表都通过 task_id 关联 review_task。 具体关系： review_task.id = pull_request_info.task_id review_task.id = review_result.task_id review_task.id = risk_item.task_id review_task.id = model_call_log.task_id

### 2. 关系图说明

review_task │ ├── pull_request_info │ 一个任务对应一个 PR 信息 │ ├── review_result │ 一个任务对应一个 AI Review 报告 │ ├── risk_item │ 一个任务对应多个风险项 │ └── model_call_log

## 一个任务对应多条模型调用日志

## 八、索引设计

为了提高查询效率，需要设计必要索引。

### 1. review_task 表索引

idx_repo_pr(repo_owner, repo_name, pr_number) 用于根据仓库和 PR 编号查询历史分析记录。 idx_status(status) 用于查询不同状态的任务，例如 RUNNING、FAILED。 idx_created_at(created_at) 用于按时间倒序查询历史任务。

### 2. risk_item 表索引

idx_task_id(task_id) 用于查询某个任务下的所有风险项。 idx_risk_level(risk_level) 用于按风险等级筛选高风险、中风险、低风险问题。 idx_file_path(file_path) 用于后续按文件路径查询风险项。

### 3. model_call_log 表索引

idx_task_id(task_id) 用于查询某个任务的模型调用记录。 idx_model_name(model_name) 用于统计不同模型的调用情况。 idx_call_type(call_type) 用于统计不同分析阶段的模型调用情况。

## 十二、数据写入流程

用户提交 PR 后，数据库写入流程如下：

### 1. 创建 review_task 记录，状态为 PENDING

### 2. 开始分析后，将状态更新为 RUNNING

### 3. 调用 GitHub API，写入 pull_request_info

### 4. 调用 AI 模型，写入 model_call_log

### 5. 解析 AI 返回结果，写入 review_result

### 6. 保存风险项，写入 risk_item

### 7. 统计风险数量，更新 review_task.risk_count

### 8. 分析成功后，将 review_task.status 更新为 SUCCESS

### 9. 如果任意步骤失败，将 review_task.status 更新为 FAILED，并写入 error_message

## 十三、数据查询流程

前端查询 Review 结果时，后端查询流程如下：

### 1. 根据 task_id 查询 review_task

### 2. 根据 task_id 查询 pull_request_info

### 3. 根据 task_id 查询 review_result

### 4. 根据 task_id 查询 risk_item 列表

### 5. 组装成 ReviewResultResponse

### 6. 返回给前端展示

返回给前端的数据结构大致如下： { "task":{}, "pullRequest":{}, "reviewResult":{}, "riskItems":[] }

## 十四、数据安全设计

数据库中可能保存 PR 信息、AI 分析结果和部分代码片段，因此需要注意数据安全。 主要措施包括： 不保存 GitHub Token 和模型 API Key； 密钥只通过环境变量或配置中心读取； 日志中不打印敏感信息； 私有仓库分析结果后续需要增加用户权限控制； 可对 raw_ai_response 和 code_snippet 控制保存长度； 对长期不用的历史分析数据可定期清理； 后续支持用户删除分析记录。

## 十六、数据库设计总结

本项目数据库以 review_task 为核心主表，通过 task_id 关联 PR 信息、AI 分析结果、风险项和模型调用日 志。这样的设计结构清晰，能够完整支撑 AI PR Review 助手第一版核心功能。 第一版重点保存以下内容： 任务信息 PR 基本信息 AI Review 报告 风险代码项 模型调用日志 该设计既能满足当前“输入 PR → 获取 diff → AI 分析 → 展示报告”的核心链路，也为后续扩展私有仓库、多用 户系统、GitHub 自动评论、团队规则配置和模型调用成本统计预留了空间。
