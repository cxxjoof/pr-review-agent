# AI PR Review 助手需求分析

## 一、项目背景

在团队协作开发中，Pull Request 是代码合并前最重要的质量控制环节。传统 PR Review 主要依赖人工检查，虽然能发现代码风格、逻辑漏洞、潜在 Bug 和架构问题，但也存在效率低、遗漏率高、Review 标准不统一等问题。尤其当 PR 修改文件较多、涉及上下文复杂或开发者时间紧张时，人工 Review 很容易只关注表面代码差异，而忽略潜在风险。

因此，本项目计划开发一个 **AI PR Review 助手**。用户只需要指定 GitHub 仓库和 PR 编号，系统即可自动获取该 PR 的代码变更内容，并结合 AI 模型进行分析，生成变更总结、风险代码识别和 Review 建议，帮助开发者更快理解 PR 内容，提高代码审查效率和质量。

## 二、目标用户与真实需求

本工具主要面向以下几类用户：

第一类是普通开发者。他们希望在提交 PR 后，能够提前获得一份自动化 Review 结果，发现明显问题，减少被人工 Reviewer 反复指出低级错误的情况。

第二类是代码 Reviewer 或项目维护者。他们通常需要在短时间内阅读大量 PR，希望工具能先帮他们总结本次变更内容，标出高风险文件和关键代码片段，从而减少理解成本，把精力集中在真正需要人工判断的地方。

第三类是团队负责人或技术负责人。他们关注代码质量、潜在风险和团队协作效率，希望通过 AI Review 工具形成更统一的 Review 标准，并在项目中逐渐沉淀代码规范和审查经验。

综合来看，开发者在代码评审中的核心需求主要包括：

1. 快速理解 PR 做了什么，而不是逐个文件慢慢阅读。
2. 发现可能存在 Bug、异常处理缺失、边界条件不足、安全隐患或性能问题的代码。
3. 针对具体代码给出可执行的 Review 建议，而不是泛泛而谈。
4. 尽量减少误报，避免 AI 对正常代码提出无意义建议。
5. 控制响应速度，不能让开发者等待太久。
6. 支持结合项目上下文，而不是只看单行 diff。
7. 输出结果清晰易读，方便开发者直接用于 Review 或修改代码。

## 三、功能需求

### 1. GitHub PR 获取功能

系统应支持用户输入 GitHub 仓库地址和 PR 编号，自动调用 GitHub API 获取对应 PR 的基础信息，包括 PR 标题、描述、作者、分支信息、修改文件列表、代码 diff 内容、提交记录等。

该功能是整个系统的入口，要求能够正确识别公开仓库的 PR 信息。后续可扩展支持私有仓库，需要用户配置 GitHub Token。

### 2. PR 变更总结功能

系统需要对 PR 的整体变更进行总结，帮助 Reviewer 快速理解本次修改的主要内容。总结内容应包括：

* 本次 PR 的主要目的；
* 修改了哪些模块或文件；
* 新增、删除或修改了哪些核心逻辑；
* 是否涉及接口、配置、数据库、依赖或测试文件变化；
* 对项目功能可能产生的影响。

该功能重点解决“Reviewer 不知道这个 PR 到底改了什么”的问题。

### 3. 风险代码识别功能

系统需要根据代码 diff 和上下文信息，识别可能存在风险的代码区域。风险类型可以包括：

* 空指针、越界、类型错误等潜在 Bug；
* 异常处理缺失；
* 输入校验不足；
* 权限控制或敏感信息泄露风险；
* SQL 注入、命令注入等安全问题；
* 性能较差的循环、查询或资源使用方式；
* 删除关键逻辑但没有补充测试；
* 修改核心模块但影响范围不明确；
* 配置文件、依赖版本或环境变量变更带来的风险。

系统应尽量给出风险位置、风险原因和可能影响，而不是只简单提示“这里可能有问题”。

### 4. Review 建议生成功能

系统需要基于分析结果生成 Review 建议。建议应尽量具体、可操作，例如：

* 建议补充边界条件判断；
* 建议增加异常处理；
* 建议补充单元测试；
* 建议拆分复杂函数；
* 建议优化变量命名或代码结构；
* 建议确认某个接口变更是否兼容旧逻辑；
* 建议检查配置变更是否会影响部署环境。

Review 建议应区分严重程度，例如高风险、中风险、低风险，方便开发者优先处理重要问题。

### 5. 误报与漏报控制功能

AI Review 工具不能只追求“多提问题”，否则会产生大量无意义建议，影响使用体验。因此系统需要在提示词和分析流程中控制误报。

具体要求包括：

* 对没有充分证据的问题，使用“建议确认”而不是直接下结论；
* 不对单纯代码风格问题过度评价；
* 优先关注和业务逻辑、安全、稳定性、性能相关的问题；
* 对正常代码不强行找问题；
* 输出中说明判断依据，让用户知道 AI 为什么这样认为。

同时，为了减少漏报，系统需要关注高风险文件和关键变更，例如认证授权、支付、订单、数据库操作、配置文件、CI/CD 文件等。

### 6. 上下文获取功能

单纯分析 diff 可能会导致 AI 理解不完整。因此系统需要设计合理的上下文获取方式。第一阶段可以先基于 PR diff 进行分析，保证实现简单、响应较快。后续可以进一步获取相关文件内容，例如：

* 被修改文件的完整内容；
* 被调用函数或类的定义；
* 相关测试文件；
* README 或项目结构说明；
* 依赖配置文件；
* 历史提交或相似代码。

通过补充上下文，AI 能更准确判断某段代码是否真的有问题，减少误报和漏报。

### 7. 结果展示功能

系统需要将 AI 分析结果以清晰结构展示给用户。建议输出结构包括：

* PR 基本信息；
* 本次变更总结；
* 重点修改文件；
* 风险代码列表；
* Review 建议；
* 建议补充的测试点；
* 总体评价。

如果后续做成 Web 页面，可以将风险项按严重程度分组展示，并支持点击跳转到对应文件和代码行。

## 四、非功能需求

### 1. 分析准确性

系统应尽量保证 AI 分析结果与真实代码变更相关，避免输出空泛、模板化的内容。分析时应结合文件类型、代码位置和上下文信息，重点关注对项目质量有实际影响的问题。

### 2. 响应速度

PR Review 需要较好的实时性。对于小型 PR，系统应尽快返回结果；对于大型 PR，可以采用分文件分析、分块处理、异步任务等方式，避免一次性把所有内容都交给模型导致响应过慢或超出上下文限制。

### 3. 可用性

工具使用流程应尽量简单。用户只需要输入仓库地址和 PR 编号，即可获得分析结果。输出内容要清晰、分层明确，避免大段难读文本。

### 4. 可扩展性

系统后续应方便扩展更多功能，例如支持私有仓库、GitLab、企业代码规范、自动生成 GitHub Review Comment、自动生成测试建议、接入 CI/CD 流程等。

### 5. 安全性

如果支持私有仓库，需要保护用户 GitHub Token 和代码内容，避免敏感信息泄露。系统不应在日志中明文保存密钥，也不应将敏感代码随意暴露给无关第三方。

## 五、系统核心流程

用户首先输入 GitHub 仓库地址和 PR 编号。系统调用 GitHub API 获取 PR 信息和代码 diff。然后系统对 diff 内容进行预处理，包括按文件拆分、过滤无关文件、提取关键变更、控制上下文长度等。接着系统将处理后的内容提交给 AI 模型进行分析，生成 PR 总结、风险识别和 Review 建议。最后系统将结果整理成结构化报告返回给用户。

整体流程可以概括为：

用户输入 PR 信息 → 获取 GitHub PR 数据 → 解析代码变更 → 补充必要上下文 → 调用 AI 模型分析 → 生成 Review 报告 → 展示给用户。

## 六、模型选择设计思路

模型选择方面，第一阶段可以优先使用通用大语言模型，例如 GPT、Claude、DeepSeek、Qwen 等具备代码理解能力的模型。选择模型时主要考虑以下因素：

* 代码理解能力是否足够强；
* 上下文窗口是否能够容纳较大的 diff；
* 响应速度是否满足使用需求；
* 调用成本是否可接受；
* 是否支持结构化输出；
* 是否适合私有化部署或企业环境使用。

对于普通场景，可以使用成本较低、速度较快的模型完成 PR 总结和基础风险识别；对于核心模块或高风险 PR，可以使用能力更强的模型进行深度分析。后续也可以设计多模型策略，例如先用轻量模型做初筛，再用强模型分析重点风险代码。

## 七、上下文获取方式设计思路

上下文获取是影响 AI Review 准确性的关键。第一版系统可以采用“PR diff 优先”的方式，只分析本次修改内容，降低实现复杂度和响应时间。

后续可以升级为“diff + 相关上下文”的方式。系统根据修改代码自动定位相关函数、类、调用链和测试文件，并将这些内容一起提供给模型。例如，当 PR 修改了某个函数调用时，系统可以额外获取该函数定义；当 PR 修改了接口逻辑时，系统可以获取相关路由、服务层和测试文件。这样 AI 的判断会更接近真实人工 Review。

进一步扩展时，还可以引入 RAG 检索机制，将项目代码切片并建立索引，在 Review 时根据变更内容检索相关代码片段，为模型提供更完整的上下文。

## 八、未来扩展方向

后续系统可以从以下几个方向继续完善：

第一，支持直接在 GitHub PR 页面自动发表评论，让 AI Review 结果能够进入真实开发流程。

第二，支持团队自定义 Review 规则，例如代码规范、安全规范、数据库规范、接口规范等，使 AI 建议更符合团队习惯。

第三，支持测试建议生成，根据代码变更自动提示需要补充哪些单元测试、接口测试或边界测试。

第四，支持历史问题学习，将过去人工 Review 中经常出现的问题沉淀为规则，提高后续 Review 的准确性。

第五，支持多平台接入，例如 GitLab、Gitee、Bitbucket 等。

第六，支持 CI/CD 集成，在 PR 创建或更新时自动触发 AI Review，形成自动化代码质量检查流程。

第七，支持风险评分机制，根据修改文件类型、代码复杂度、测试覆盖情况和 AI 分析结果，为 PR 生成综合风险分数。

## 九、总结

AI PR Review 助手的核心价值不是完全替代人工 Review，而是帮助开发者和 Reviewer 更快理解代码变更、提前发现明显风险、提高 Review 的效率和质量。系统应重点解决 PR 理解成本高、问题发现不及时、Review 标准不统一等痛点。通过 GitHub PR 数据获取、代码 diff 解析、AI 智能分析、风险识别和建议生成，本工具可以成为开发流程中的辅助审查工具。

在设计上，系统需要平衡准确性、响应速度和使用体验。第一阶段可以先实现公开仓库 PR 的自动分析，后续再逐步扩展上下文检索、私有仓库支持、GitHub 评论集成、多模型策略和团队规则配置等能力。
